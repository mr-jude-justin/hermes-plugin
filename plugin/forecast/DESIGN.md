## 0. 两篇论文里决定设计方向的事实

| 事实 | 出处 | 对我们的含义 |
|---|---|---|
| 同一任务多次运行：平均最贵一次约是最便宜一次的 **2 倍**，极端情况可差 **30 倍**；人类判断的难度和 token 用量只是弱相关（Kendall τ = 0.32） | 2604.22750 | 必须给区间，P90 要放宽；不能指望靠"难度"来判档 |
| 成本主要是输入，尤其是缓存读取；GPT-5.4 在 SWE-bench 上 99% 是输入 token | 两篇都有 | 预测重点是"跑几步"和"上下文涨多快"，输出只是小头 |
| 让模型自己估：相关系数最多 0.39，系统性低估；TokenCast 中 Self-Prediction 的 90% 区间实际只覆盖 52.7% | 2604.22750；TokenCast 表 3 | L3 只当"步数/档次"的参考信号，绝不用它出区间 |
| **任务开始前**，TokenCast 的 MAE 比最强对手还差 2.2%（24 个组合里输 15 个），覆盖率只有 82% | TokenCast | 开工前的报价本来就难准。粗分档加历史中位数，已经接近当前最好水平 |
| **跑到一半**（Task Update）MAE 降 27.8%，覆盖率 91.2% | TokenCast | 真正的价值在中途重新预测，也就是"预计超预算，先停下来问" |
| 基学习器对比（相对历史中位数的 MAE）：Ridge 0.93，RF 0.81，XGBoost 0.73，LightGBM 0.69 | TokenCast D.6 | LightGBM 最好，但它是在约 1.1 万条轨迹上训练的。我们只有 20–30 条，先不做 |
| 换成没见过的任务类型时，零样本误差是 Self-Prediction 的 1.3–1.5 倍；有 20 个目标任务后降到 0.82–0.85 | TokenCast | 冷启动用默认值，用户攒到约 10–20 个任务后，历史数据开始主导 |
| 关键特征：请求长度、上一轮输入 token、剩余计划条数、连续无进展的调用次数 | TokenCast 图 5 | 需要 Justin 在 harness 里收集这些（见第 6 节） |

另外两点需要说明：
- 回归方法上，相关研究（输出长度预测、LLM 调度）普遍对 log 目标做回归或分位数预测，原因就是分布重尾。分桶分类这条路已经被证明效果不如排序或回归。
- 以下内容 TokenCast **没有**验证过：缓存、上下文压缩、子 agent、图片和视频的按次计费。这些部分需要我们自己用 Hermes 上的真实轨迹来测。

## 1. 核心模型：段代数（取自 TokenCast，不需要训练就能用）

记第 k 次调用开始时的上下文长度为 L_k，每步净增长为 g，共 K 次调用，每次的输出为 o。则：

```
L_k = L_1 + g·(k−1)
总输入 ≈ K·L_1 + g·K(K−1)/2        ← 关于步数是二次的，这正是长任务贵的原因
总输出 ≈ K·o
```

TokenCast 的写法是用段三元组 (n, g, b) 来组合：`b = C − n·L`，两段拼接时有 `C_{A∘B} = (n_A+n_B)L_A + b_A + b_B + n_B·g_A`。上面的公式就是 b 取线性增长时的特例。

拆分成 `{input, cache_read, cache_write, output}`（cache_write 是 Justin 提议新增的字段，待确认）：
- cache_write：第一次调用时，如果缓存是冷的，约等于 L_1（Hermes 实测约 68k）；之后每步约等于新增的内容 g
- cache_read ≈ 每步复用的上一轮上下文 ≈ h·L_k，h 是缓存命中率，从用户历史中学习。冷启动时：Anthropic 取 0.9（实测后续调用约读 84k），未知 provider 取 0
- input（未缓存部分）≈ 总输入 − cache_read − cache_write
- output ≈ K·o

**固定底数**：每轮对话至少会有一次调用，每次都带着约 70–85k 的系统提示词和工具定义（Hermes v0.23.0 实测）。这部分不用预测，直接从 L_1 和用户当前的配置中得到。

**时间限制**：hook 超过 30 秒会被跳过并且直接放行（fail-open），所以 `estimate()` 总耗时要控制在约 3 秒内：L1 + L2 加起来低于 50 ms，L3 约 0.5 秒。L3 需要用户授权 `allow_model_override`；没有授权时跳过 L3。

这样，算法只需要预测四个量：**K（步数）、L_1、g、o**，再加上 h。L_1 在开工时已知（`context_tokens_now` 加上消息长度），所以真正需要预测的主要是 K 和 g。

## 2. 分档标准（初稿 v2，根据 Justin 11/6 实测修订）

**Hermes 实测有一个很大的固定底数**（Justin 用 v0.23.0 测得）：
- 只回一句 "ok"，第一次调用就有约 68k prompt token，主要是系统提示词加工具定义，基本都是 cache_write；
- 之后每次调用还要从缓存读约 84k。

论文里 SWE-bench 每次调用平均只有约 12k 上下文，所以**论文给的 token 绝对值不能直接拿来当 Hermes 的档次边界**。

因此，档次**按步数 K 划分**，不按 token：
- 步数与 harness 无关，也与模型无关；
- token 区间由第 1 节的公式加上实测的 L_1 算出来，底数会自动算进去。

另外有一个例外：如果单步上下文已经很大（长文档任务，或 `context_tokens_now` 很高），就直接升一档。

| 档 | 典型任务 | 步数 K（P50 / P90） | 总 token P50 / P90（算例） | 论文锚点（调用次数） |
|---|---|---|---|---|
| **S** | 闲聊、单问单答、解释一段代码 | 2 / 4 | 约 160k / 350k | MMLU-Pro：4–6 |
| **M** | 查资料、小改动、单文件修复 | 8 / 20 | 约 700k / 2.2M | Search-R1：约 8 |
| **L** | 多文件 bug 修复、中等功能 | 20 / 50 | 约 2.2M / 7.5M | SWE-bench：约 20 |
| **XL** | 长线重构、新模块、读整个仓库或长文档 | 60 / 150 | 约 10M / 40M | 长线任务，再叠加 30 倍的方差尾部 |

**算例的假设**：L_1 = 80k，g = 3k/步，o = 1k/步。实际运行时，L_1 用 `context_tokens_now`，g 和 o 从历史中学习。

- 其中**绝大部分是 cache_read**（价格约为未缓存输入的 1/10），所以换算成美元后，比 token 数看起来"温和"得多。这也说明拆分 cache_read 和 cache_write 是成本准确的关键。
- P90 约为 P50 的 2.5 倍（步数），换算成 token 后约 3–4 倍。这是按"同任务最多差 30 倍"和"开工时覆盖率只有 82%"刻意放宽的。用户历史足够后，改用第 4 节的校准结果替换。
- 档次只是对外展示的标签，加上冷启动时的先验。内部用来出区间的是连续预测值，不会卡在档次边界上。
- 按次收费的工作（例如图片生成）**不进入**token 档次，单独放进 `per_call_units`。L1 规则根据关键词和启用的 `image_gen` 工具集来估计张数。
- 这些数字都来自公开 benchmark，**和 Hermes 上的真实分布是否一致还不知道**。第一批 eval 轨迹出来后要重新定档。

### 2.1 第二个维度：任务类型（决定成本的"形状"）

2604.22750 把编程类任务分成三种场景：
- **code reasoning**：理解代码
- **coding chat**：贴一段代码、来回问答
- **agentic coding**：模型在真实环境里自己干活

再加上我们自己要支持的查资料和生成类任务，同样大小的任务，不同类型的成本结构差别很大。所以要用**两个维度**：

- **档次（S/M/L/XL）决定"跑多少步"**，也就是 K。
- **类型决定"每一步长什么样"**：每步上下文涨多少 g、每步输出多少 o、缓存命中率 h，以及会经过哪些阶段。

| 类型 | 识别信号（L1） | 常见档次 | g（每步上下文增长） | o（每步输出） | 特点 |
|---|---|---|---|---|---|
| **chat**：闲聊、一般问答 | 短问句，没有代码、路径或 URL | S | 约 1k | 约 0.5k | 几乎就是固定底数 |
| **coding chat**：贴代码问答 | 有代码块，但没让它去动仓库 | S–M | 约 1–2k | 约 1.5k | 输出占比最高（要写代码给用户） |
| **code reasoning**：读懂、解释、审查代码 | "为什么 / 解释 / review / 看看这个模块" + 路径或仓库 | M–L | 约 5–8k（读文件） | 约 1k | 以读为主，g 大；几乎不跑测试 |
| **agentic coding**：改代码、修 bug、实现功能 | "修 / 实现 / 重构 / 加测试" + git 仓库 + terminal/file 工具集 | L–XL | 约 3k | 约 1k | 步数多，有阶段，最难预测 |
| **research**：联网查资料 | "查 / 调研 / 搜索 / 最新" + web 工具集 | M–L | 约 6–10k（网页内容大） | 约 1.5k | 每一步的 g 波动大 |
| **generation**：生成图片等 | "画 / 生成图片" + image_gen 工具集 | S | 小 | 小 | 主要成本在 `per_call_units`，token 只是零头 |
| **delegated / multi-agent**：派子 agent 并行做 | 启用了 delegate 工具；"分头 / 并行 / 多个方向" | L–XL | 每个子 agent 各自 | 各自 | 每个子 agent 都有**自己的固定底数**（系统提示词加工具）。Anthropic 报告：agent 约为 chat 的 4 倍 token，多 agent 约为 15 倍 |
| **browser / computer use**：靠截图操作网页或桌面 | 启用了浏览器或截图类工具 | M–XL | 每张截图约 1–2k，历史截图会累积 | 小 | 每步都要看截图，步数又多。有博客实测一个任务 551k，而用 API 只要 12k（约 45 倍，未经同行评审） |
| **long-doc / RAG**：读大量文档后回答 | 附件多，或"读完 / 总结这些文件" | M–XL | 第一步就很大 | 中 | 步数少但 L_1 巨大，按"长上下文信号"升档 |

规模参照（数字来自论文和厂商报告，不是 Hermes 实测）：
- agentic coding 的 token 量超过单轮 code reasoning 的 **1000 倍**，输入与输出之比超过 **150:1**（2604.22750；2605.09104 转引）。
- 多 agent 框架的输入与输出之比只有 2:1 到 3:1（AgentTaxo，2605.09104 转引），说明子 agent 之间的通信也很耗输出。
- ChatDev 中，迭代式 code review 占了 59.4% 的 token。这说明"来回修改"类循环本身就是大头。

- 表中 g 和 o 的数值都是**冷启动猜测**，没有经过验证。之后从 eval 结果和用户历史中，按类型分别学习，存进 `forecast_state`。
- 一个任务可以是混合类型，例如"先查资料再改代码"。这时按信号强度给出各类型的权重，g 和 o 取加权值；`Estimate.basis` 里写主类型。
- L2 历史近邻的检索**优先在同类型内进行**，同类型数量不够时，再放宽到全部历史。

### 2.2 阶段（主要用于 agentic coding）

2604.22750 把编程 agent 的执行过程分成五个阶段：setup → explore → fix → validate → closeout。这和 TokenCast 的段代数正好对应：**每个阶段就是一段**，各自有自己的 (n, g, b)。

| 阶段 | 识别方式（看最近几步的工具） | 轮数占比（2604.22750 表 1，Sonnet-4.5 在 OpenHands 上） | 主要成本来源（同一论文） |
|---|---|---|---|
| setup | 看目录、读配置、装依赖 | 9.98% | **输出**（集中在规划） |
| explore | read_file、grep、search 占多数 | 30.37% | **输入**（仓库内容不断进入上下文，g 大） |
| fix | write_file、edit 占多数 | 33.53% | 输出（写代码）加输入 |
| validate | terminal 跑测试或 lint，可能来回失败 | 16.59% | 输入（测试输出），失败时步数膨胀 |
| closeout | 总结、提交，不再调用工具 | 9.53% | 输出加输入 |

另外两点：
- 各阶段的**轮数占比**来自论文，但只有一个模型、一个框架，放到 Hermes 上要重新测。
- 论文发现：**花费越高的运行，重复查看同一个文件、重复编辑的次数越多**（图 4），作者认为这是"无效探索"。所以"重复读或写同一文件的次数"应当作为中途预测的步数膨胀信号，和 TokenCast 的"连续无进展"一起使用。

**在 `reforecast()` 中的用法：**
- 根据最近的工具判断当前处在哪个阶段。
- 剩余步数 = 当前阶段剩下的步数 + 后续各阶段的先验步数。各阶段按自己的 g 依次组合（TokenCast 公式 1）。
- 进入 validate 后**反复失败**，是步数膨胀的主要来源，对应 TokenCast 的"连续无进展"特征。这时要上调 K_rem，并加宽区间。

阶段的划分和占比都是**假设**。要用 eval 轨迹验证"按阶段预测"是否比"不分阶段的条件期望"更准；如果不更准，就去掉。

### 2.3 推理强度（effort）

**更正**：2604.22750 里**并没有**按 effort 档位（min 到 ultra）做的实验。它只把运行按实际花费分成四个四分位组，结论是：准确率在中等花费时达到顶峰，之后饱和，而高花费主要来自无效探索。所以 effort 系数完全没有文献支撑，只能靠我们自己在 eval 里测，比如同一组任务分别用 low、medium、high 各跑一遍。

effort 主要影响**输出和推理 token**（`reasoning_tokens`），也可能影响步数。

- 作为特征：`reasoning_effort`（需要向 Justin 申请，见第 6 节）。
- 模型：o 乘以一个系数 m(model, effort)。冷启动时取 low 0.6、medium 1.0、high 1.6、max 2.5，**这些都是猜测**；之后按 (模型, effort) 从历史中学习。
- 因为输入占了绝大部分 token，effort 对**总 token** 的影响有限；但输出单价高，所以对**美元**的影响不能忽略。

### L1 规则怎么判档（< 1 ms）

先给打分项，再按分数映射到档次：
- **S 信号**：消息很短（< 40 字），是问句或闲聊；没有代码块、路径或 URL；没有附件。
- **升档信号**：
  - 关键词，中英文都要覆盖："重构 / refactor"、"实现 / implement"、"整个项目 / whole repo"、"迁移 / migrate"、"写测试 / add tests"、"调研 / research"、"读完这些 / summarize these files"
  - 消息里出现的路径或文件数
  - 有附件
  - `repo_size.lines` 很大（比如超过 5 万行时上调半档）
  - 启用了 terminal 或 file 工具集，并且 `cwd_is_git_repo`
- **长上下文信号**：`context_tokens_now` 已经很大时，即使步数少也要上调，因为每步都要重读这些上下文。

## 3. 开工前的预测 `estimate()`

```
先验（档次默认分布）
   ⊕ L2 历史近邻：TF-IDF（词 1–2 gram + 字符 3–5 gram，和 TokenCast 一致）+ 余弦相似度，取 top-k，k 约为 8
   ⊕ L3 便宜模型：只在 L1、L2 拿不准时调用，只输出 K 和档次
→ 在 log 空间做收缩加权：w_hist = n_sim / (n_sim + 5)
→ P50 = 加权后的中位数；P90 由第 4 节校准得到
```

- 历史里的 token 要按模型做归一化。TokenCast 中同一任务在 Opus 和 GPT 上相差 1.05 到 1.8 倍，所以给每个模型维护一个乘数，作为校准参数存进 `forecast_state`。
- `confidence` 由历史近邻的数量和相似度，以及 L1 和 L2 是否一致决定。
- `layer_used` 和 `basis` 照实填写，例如 `"8 similar past tasks + rules"`。

## 4. 区间校准（用于 `record_outcome()`）

- 每完成一个任务，记录 log 比值 `r = log(actual_total / P50_pred)`。
- **P90 = P50 × exp(r 的经验 0.9 分位)**，这就是 split conformal 的一维版本，不需要任何模型。TokenCast 的做法是先用 LightGBM 出分位数，再用 conformal 平移，我们是它的简化版。
- 当 r 的样本少于 10 个时，用档次的默认倍数（3.5 倍）。超过 10 个之后，用收缩混合逐步过渡到经验值。
- 同时修正系统偏差：如果 r 的中位数 ≠ 0，说明整体高估或低估，就用它来修正各档和各模型的乘数。
- 所有校准参数都存进 `forecast_state`。

## 5. 跑到一半重新预测 `reforecast()`（产品价值所在）

已知：已花费 S_k、已执行步数 k、最近每一步的 `Usage`，以及最初的 `original` 预测。

1. 用最近 5 到 10 步的 L_j 做最小二乘，得到增长率 ĝ；对最近几步取中位数，得到 ô 和缓存命中率 ĥ。
2. 估计剩余步数 K_rem，按信号强弱依次取用：
   - **计划或待办剩余条数**（TokenCast 中重要度 0.25）× 每条计划的平均步数；
   - 否则用条件期望 E[K − k | K > k]：从同档历史的 K 分布中计算；没有历史时，用档次先验（对数正态）计算；
   - **连续无进展的调用或连续报错**（重要度 0.23）出现时，把 K_rem 往上推，并加宽区间。
3. 剩余量 `R = K_rem·L_k + ĝ·K_rem(K_rem−1)/2 + K_rem·ô`，按 ĥ 拆分成三项。
4. 最终预测 T̂ = S_k + R̂。区间的**下界不低于已花费 S_k**，这一点与 TokenCast 相同。
5. 与 `original` 比较，算出偏差。如果偏差很大，就提高区间宽度，并把这条信息写进 `basis`。

Harness 在每次 `pre_tool_call` 时拿 P90（换算成美元后）去和上限比较，决定是否拦截。

## 6. 需要向 Justin 申请的特征（待 Eason 确认后，按 4.3 格式发到 board）

1. **每次调用的用量明细**：已经有了。Justin 实测，`post_api_request` 的 usage 包含 input、output、cache_read、cache_write、reasoning、prompt_tokens 等字段，L_k 可以直接用 `prompt_tokens`。需要请 Justin 把**每一步**的 `Usage` 按顺序传进 `recent_steps`，并把 cache_write 和 prompt_tokens 都保留下来。
2. **计划或待办的条数**（总数、已完成数），前提是 Hermes 有 todo 工具。用途：估计 K_rem。来源 hook 猜测是 `pre_tool_call` 或 `post_api_request`。
3. **工具报错、重试、连续无进展的计数**。用途：中途加宽区间。来源 hook 猜测是 `pre_tool_call` 和 `post_api_request`。
4. **每个子 agent 的用量归属**（`subagent_start` / `subagent_stop`）。用途：按模型归一化，并单独计账。
5. **推理强度 `reasoning_effort`**（当前会话的设置）。用途：给 o 乘系数（见 2.3）。来源猜测：会话配置，或者 `pre_llm_call` 的参数。
6. **每一步调用了哪些工具**（按步排列的工具名，以及成功或失败），而不只是 `recent_tools` 的汇总。用途：识别当前阶段（见 2.2）。来源 hook 猜测是 `pre_tool_call`。

## 6.5 算法升级（第二轮文献调研后加入，按优先级排列）

1. **分层经验贝叶斯收缩**（替换第 3 节里拍脑袋定的 `w = n/(n+5)`）
   - 在 log token 空间建立层级：全局 → 类型 → (类型, 档次) → 相似历史任务。每一层的均值都向上一层收缩，收缩强度由该层的样本数和方差决定。
   - 用户数据少的时候自动靠近先验，数据多了自动靠近自己的历史，冷启动和"越用越准"由同一个公式解决。
   - 参照：用户会话时长预测里的层级收缩（arXiv 1803.01440），以及 Dynamic Hierarchical Empirical Bayes（arXiv 1809.02213）。
2. **用离散时间风险模型（hazard model）预测剩余步数**（替换第 5 节里的条件期望）
   - 每一步估计 P(在第 k 步结束 | 还没结束, 当前阶段, 连续无进展次数, 报错次数, 重复读写文件次数)，用 logistic 回归来拟合，参数很少，小数据也能训练。
   - 这样做天然支持**右删失**：被预算拦停的任务（`outcome="stopped"`）可以正确地用于训练，不会把预测越校越低。
   - 参照：在 agent 多轮一致性研究中用了 Kaplan-Meier 曲线和离散时间 logistic hazard（arXiv 2609.29508）。
   - 冷启动时，用 2.2 节的阶段占比和档次的步数先验，构造一个分阶段的 hazard 先验。
3. **在线自适应 conformal**（ACI，加在第 4 节的区间上）
   - 每完成一个任务，按 `α ← α + γ·(0.1 − 是否超出 P90)` 更新一次分位数。用户的任务类型会随时间变化，这样能保持覆盖率在 90% 附近，而不只是在历史上平均达到 90%。
   - 注意：conformal 方法在样本少、分布偏斜时区间会偏宽（相关文献已经指出）。这正好和"开工时宁宽勿窄"的目标一致。
4. **子 agent 作为独立段**：每个子 agent 自带固定底数 L_1，按 N_sub × (底数 + 自身段) 计算，再和主 agent 的段组合。N_sub 从计划或者 delegate 调用中读取。
5. **中途信号再补一个**："重复查看或编辑同一文件"的计数（2604.22750 图 4），作为 hazard 模型的特征。

## 8. 评估（`eval/`）

- 20 到 30 个任务，按**类型 × 档次**分层抽样：每种类型至少 3 个，agentic coding 多放一些（因为最难预测）。每个任务至少跑 2 次（同一任务方差很大）。
- 结果要按类型分别报告误差。这样才知道类型这个维度到底有没有带来提升，以及哪一类最不准。必须用 **API key** 跑，不能用订阅登录（见 plan 第 1 节）。
- 对比对象：
  - 历史中位数（TokenCast 的归一化基准）
  - L1 单独
  - L1 + L2
  - 完整版
  - Self-Prediction（直接问主模型）
- 指标：
  - log 空间的 MAE 和 WAPE
  - P90 的实际覆盖率，目标约 90%
  - 档次准确率
  - 中途重新预测：在 25%、50%、75% 进度时，误差各下降多少
- 原则：准确率要实际测出来，不能直接照搬论文数字。
