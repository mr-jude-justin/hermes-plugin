## 接口一览（harness 怎么调用）

```python
from .forecast import configure, estimate, reforecast, record_outcome, projected_steps

configure(state, history=None, llm=None, l3_mode="auto")  # register() 里调用一次。不读不写，第一次 estimate 时才读历史
estimate(features) -> Estimate        # 开工前：L1 → L2（有相似历史时）→ L3（启用且没把握时）→ 校准（有足够记录时）
reforecast(features, original, spent, steps_done, recent_steps) -> Estimate   # 每次 API 调用后
record_outcome(features, estimate, actual, steps, outcome)                    # 每个任务结束时
projected_steps(estimate, "p50" | "p90") -> list[Tokens]                      # 逐步展开，按每次调用计价
```

**`Estimate` 各字段由谁填：**

| 字段 | 填写方 | 说明 |
|---|---|---|
| `tier`、`task_type` | 算法 | 档次按 P50 步数算；类型来自 L1 |
| `tokens_p50`、`tokens_p90` | 算法 | 整数四项拆分。reforecast 的结果**包含已花费部分**，且不低于已花费 |
| `est_steps`、`est_steps_p90` | 算法 | 主 agent 的总步数（不含子 agent） |
| `per_call_units` | 算法 | 例如 `{"image_gen": 3}` |
| `confidence`、`basis` | 算法 | basis 例如 `"3 similar past tasks (top sim 0.67, weight 0.45) + rules: ...; calibrated x0.62, P90 level 0.91 (n=12)"` |
| `layer_used` | 算法 | `"L1"`、`"L2"`、`"L3"` 或 `"reforecast"`。L3 只在没有 L2 近邻时才会标成 `"L3"`；校准不单独标层，只写在 basis 里 |
| `estimate_cost_usd` | 算法 | L3 这次调用的花费（harness 已经算好价格传回来，再由它记进账本）；没调用 L3 时为 0 |
| `cost_usd_p50`、`cost_usd_p90` | harness | 用 `projected_steps` 逐步计价 |
| `shape` | 算法 | 见下 |

**`shape` 的格式：**

```json
{
  "start_prompt": 70012, "growth": 3000.0, "output_per_step": 1000.0,
  "cache_hit": 0.9, "warm_cache": false,
  "draft_p50": 1990000, "draft_p90": 7200000,
  "steps_done": 10,
  "subagents": {"count_p50": 3, "count_p90": 3, "steps_p50": 8, "steps_p90": 20,
                "start_prompt": 52600, "growth": 8000, "output_per_step": 1500, "cache_hit": 0.9}
}
```

- `draft_p50/p90`：校准前的总量，只供 `record_outcome` 校准使用，harness 不用管。
- `l3_steps`：L3 原始猜测的步数（只有 L3 运行过才有），记进 L2 记录，用来学习它低估了多少倍。
- `steps_done`：只有 reforecast 的结果才有。有这个字段时，`shape` 和 `projected_steps` **只描述剩下的调用**，harness 按剩余步骤计价后再加上已花的钱（harness `core.py` 中的 `_reforecast` 已经这样实现）。
- `subagents`：只有派子 agent 的任务才有。`projected_steps` 先列主 agent 的调用，再追加每个子 agent 的调用。

**存储**：L2 索引存在 `ForecastState["l2_records"]`，是一个 JSON 列表，最多 500 条。每个任务结束只写一次。记录里**没有原文**，只有哈希后的计数（测试中有专门检查）。harness 在 `record_outcome` 调用之后才清空 `message`。

## 0. 两篇论文里决定设计方向的事实

| 事实 | 出处 | 对我们的含义 |
|---|---|---|
| 同一任务多次运行：平均最贵一次约是最便宜一次的 **2 倍**，极端情况可差 **30 倍**；人类判断的难度和 token 用量只是弱相关（Kendall τ = 0.32） | 2604.22750 | 必须给区间，P90 要放宽；不能指望靠"难度"来判档 |
| 成本主要是输入，尤其是缓存读取；GPT-5.4 在 SWE-bench 上 99% 是输入 token | 两篇都有 | 预测重点是"跑几步"和"上下文涨多快"，输出只是小头 |
| 让模型自己估：相关系数最多 0.39，系统性低估；TokenCast 中 Self-Prediction 的 90% 区间实际只覆盖 52.7% | 2604.22750；TokenCast 表 3 | L3 只当"步数/档次"的参考信号，绝不用它出区间 |
| **任务开始前**，TokenCast 的 MAE 比最强对手还差 2.2%（24 个组合里输 15 个），覆盖率只有 82% | TokenCast | 开工前的报价本来就难准。粗分档加历史中位数，已经接近当前最好水平 |
| **跑到一半**（Task Update）MAE 降 27.8%，覆盖率 91.2% | TokenCast | 真正的价值在中途重新预测，也就是"预计超预算，先停下来问" |
| 基学习器对比（相对历史中位数的 MAE）：Ridge 0.93，RF 0.81，XGBoost 0.73，LightGBM 0.69 | TokenCast D.6 | LightGBM 最好，但它是在约 1.1 万条轨迹上训练的。我们数据太少，先不做 |
| 换成没见过的任务类型时，零样本误差是 Self-Prediction 的 1.3–1.5 倍；有 20 个目标任务后降到 0.82–0.85 | TokenCast | 冷启动用默认值，用户攒到约 10–20 个任务后，历史数据开始主导 |
| 关键特征：请求长度、上一轮输入 token、剩余计划条数、连续无进展的调用次数 | TokenCast 图 5 | harness 已全部收集（第 6 节） |

另外两点需要说明：
- 回归方法上，相关研究（输出长度预测、LLM 调度）普遍对 log 目标做回归或分位数预测，原因就是分布重尾。所以我们所有的混合和收缩都在 log 空间里做。
- 以下内容 TokenCast **没有**验证过：缓存、上下文压缩、子 agent、图片和视频的按次计费。这些部分需要我们自己用 Hermes 上的真实轨迹来测。

## 1. 核心模型：段代数（`tokens.py`）

记第 k 次调用开始时的上下文长度为 L_k，每步净增长为 g，共 K 次调用，每次的输出为 o。则：

```
L_k = L_1 + g·(k−1)
总 prompt = K·L_1 + g·K(K−1)/2        ← 关于步数是二次的，这正是长任务贵的原因
总输出   = K·o
```

TokenCast 的写法是用段三元组 (n, g, b) 来组合：`b = C − n·L`，两段拼接时有 `C_{A∘B} = (n_A+n_B)L_A + b_A + b_B + n_B·g_A`。上面的公式就是 b 取线性增长时的特例。

**拆分成四项**：每次调用里，和上一次调用 prompt 重复的部分是"缓存前缀"（第 1 次调用时，缓存热则前缀为 L_1，冷则为 0；之后第 j 次调用的前缀是 L_{j−1}）。
- `cache_read` = h × 前缀
- `input`（未缓存）= (1 − h) × 前缀
- `cache_write` = 这次新追加的内容（冷启动的第 1 次调用会写入整个 L_1）
- `output` = o
- h = 0（provider 没有缓存）时，所有 prompt 都计为 `input`。

h 的冷启动值：模型名里含 claude/anthropic 时取 0.9（实测后续调用约读 84k），其他取 0。之后由 L2 和 reforecast 从实际数据中学习。

- `project(K, ...)` 给出闭式总量。K 可以是小数，因为它是一个分布的 P50 或 P90。
- `step_splits(K, ...)` 给出逐步的明细，K 为整数时两者的总和完全相等。
- **固定底数**：Hermes v0.23.0 每轮对话的 prompt 约 70k（系统提示词加工具定义）；每个子 agent 约 52.6k（均为 Justin 实测）。L_1 = `context_tokens_now`（没有时用 70k）+ 消息自身的 token 数。
- **时间限制**：hook 超过 30 秒会被跳过并直接放行（fail-open）。L1 每次低于 1 ms；L2 在 500 条记录时低于 50 ms（有测试）。

## 2. 分档标准（`defaults.py`）

档次**按步数 K 划分**，不按 token，原因有二：
- Hermes 的固定底数很大（约 70k），论文里 SWE-bench 每次调用平均只有约 12k 上下文，所以论文的 token 绝对值放到 Hermes 上不适用；
- 步数与 harness 无关，也与模型无关。token 区间由第 1 节的公式加上实际的 L_1 算出来，底数会自动算进去。

| 档 | 典型任务 | 步数 K（P50 / P90） | 总 token P50 / P90（算例） | 论文锚点（调用次数） |
|---|---|---|---|---|
| **S** | 闲聊、单问单答、独立小脚本 | 2 / 4 | 约 160k / 350k | MMLU-Pro：4–6 |
| **M** | 查资料、小改动、单文件修复 | 8 / 20 | 约 700k / 2.2M | Search-R1：约 8 |
| **L** | 多文件 bug 修复、中等功能 | 20 / 50 | 约 2.2M / 7.5M | SWE-bench：约 20 |
| **XL** | 长线重构、新模块、读整个仓库或长文档 | 60 / 150 | 约 10M / 40M | 长线任务，再叠加 30 倍的方差尾部 |

**算例的假设**：L_1 = 80k，g = 3k/步，o = 1k/步。

- 其中**绝大部分是 cache_read**（价格约为未缓存输入的 1/10），所以换算成美元后，比 token 数看起来"温和"得多。这也说明拆分 cache_read 和 cache_write 是成本准确的关键。
- P90 约为 P50 的 2.5 倍（按步数），这是刻意放宽的。用户历史足够后，由第 4 节的校准接管。
- **档次只是对外展示的标签。** L1 之后，档次由 P50 步数反推：按相邻档中位数的几何平均分界，即 S < 4 ≤ M < 12.6 ≤ L < 34.6 ≤ XL。
- 按次收费的工作（例如图片生成）**不进入**token 档次，单独放进 `per_call_units`。
- 这些数字都来自公开 benchmark 和 Justin 的少量实测，**和 Hermes 上的真实分布是否一致还不知道**。

### 2.1 第二个维度：任务类型（决定成本的"形状"）

- **档次（S/M/L/XL）决定"跑多少步"**，也就是 K。
- **类型决定"每一步长什么样"**：每步上下文涨多少 g、每步输出多少 o，以及会经过哪些阶段。

前三种编程场景来自 2604.22750，其余是我们的产品自己要支持的。

| 类型 | 默认档 | g（每步） | o（每步） | 特点 |
|---|---|---|---|---|
| **chat**：闲聊、一般问答 | S | 1k | 0.5k | 几乎就是固定底数 |
| **coding_chat**：贴代码问答 | S | 1.5k | 1.5k | 输出占比最高 |
| **code_reasoning**：读懂、解释、审查代码 | M | 6.5k | 1k | 以读为主，g 大 |
| **agentic_coding**：改代码、修 bug、实现功能 | L | 3k | 1k | 步数多，有阶段，最难预测 |
| **research**：联网查资料 | M | 8k | 1.5k | 网页内容大，g 波动大 |
| **generation**：生成图片等 | S | 0.5k | 0.3k | 主要成本在 `per_call_units` |
| **delegated**：派子 agent 并行做 | M | 3k | 1k | 每个子 agent 单独算一段，各自从 52.6k 的底数开始、缓存为冷（见 2.4） |
| **browser**：靠截图操作网页或桌面 | M | 1.5k | 0.5k | 截图每张约 1–2k 且会累积；有博客实测 45 倍于 API 方式（未经同行评审） |
| **long_doc**：读大量文档后回答 | M | 2k | 1.5k | 步数少但 L_1 巨大，按"长上下文信号"升档 |

规模参照（数字来自论文和厂商报告，不是 Hermes 实测）：
- agentic coding 的 token 量超过单轮 code reasoning 的 **1000 倍**，输入与输出之比超过 **150:1**（2604.22750；2605.09104 转引）。
- Anthropic 报告：agent 用的 token 约为 chat 的 4 倍，多 agent 系统约为 15 倍。
- ChatDev 中，迭代式 code review 占了 59.4% 的 token。这说明"来回修改"类循环本身就是大头。

- 表中 g 和 o 的数值都是**冷启动猜测**。L2 会从用户自己的历史中迁移实际的 g、o、h（第 3 节）。
- 混合类型（例如"先查资料再改代码"）：按得分给出各类型的权重，g 和 o 取加权平均；`task_type` 取得分最高的类型。
- L2 检索时，**同类型的近邻有 3 个以上就只用同类型的**，否则放宽到全部。

### 2.2 阶段（用于 `reforecast` 中的 agentic_coding 和 code_reasoning）

2604.22750 把编程 agent 的执行过程分成五个阶段：setup → explore → fix → validate → closeout。

| 阶段 | 识别方式（看最近 6 步的工具） | 轮数占比（2604.22750 表 1，Sonnet-4.5 在 OpenHands 上） | 阶段中点的累计占比（代码中使用） |
|---|---|---|---|
| setup | 总共不超过 2 步，且还没改过文件 | 9.98% | 5.0% |
| explore | `read_file`、`search_files` 等占多数 | 30.37% | 25.2% |
| fix | `write_file`、`patch` 占多数 | 33.53% | 57.1% |
| validate | `terminal` 占多数；或者已经改过文件，最近又在跑 terminal | 16.59% | 82.2% |
| closeout | 目前识别不出来（没有工具调用就没有信号） | 9.53% | 95.2% |

- 识别时，越近的步骤权重越高；得分打平时取更靠后的阶段。
- 由阶段推算剩余步数：`k / 累计占比 − k`。它在 log 空间里以 0.25 的权重并入剩余步数的估计（第 5 节）。
- 论文还发现：**花费越高的运行，重复查看、重复编辑同一个文件的次数越多**（图 4），作者认为这是"无效探索"。代码把它当作失控信号（第 5 节）。
- 阶段的划分和占比都只来自一个模型、一个框架，放到 Hermes 上要重新测。

### 2.3 推理强度（effort）

2604.22750 里**没有**按 effort 档位做的实验。它只把运行按实际花费分成四个四分位组，结论是：准确率在中等花费时达到顶峰，之后饱和。所以 effort 系数没有文献支撑。

- 实现：每步输出 o 乘以一个系数：minimal/min 0.4、low 0.6、medium 1.0、high 1.6、xhigh 2.0、max/ultra 2.5。**这些全是猜测。**
- 来源：`features.reasoning_effort`，由 harness 从 Hermes 配置中读取。
- 输入占了绝大部分 token，所以 effort 对 token 总数影响有限；但输出单价高，所以对美元的影响不能忽略。

### 2.4 L1 规则（`rules.py`，每次 < 1 ms）

**判断类型**（为每种类型打分，取最高分）：
- chat 有 0.5 分的保底，没有任何信号时就是 chat。
- 中英文关键词：每种类型有一组正则，命中算 1 分，每多命中一个不同的词再加 0.5 分。
- 结构信号：
  - 代码块：coding_chat +1.5
  - 路径：code_reasoning 和 agentic_coding 各 +0.3
  - URL：research +0.5/个，最多 3 个
  - 附件：long_doc +0.7（1 个）或 +1.5（多个）
  - 代码标识符（`name()`、snake_case、camelCase）：agentic_coding +0.5，code_reasoning +0.3
  - "解释 / 为什么 / explain / how does" 这类泛用词，**只有在有代码上下文时**（代码块、路径、标识符、git 仓库，或者"代码 / 函数 / file / bug"等名词）才给 code_reasoning +1，否则不加分。所以 "Explain TCP vs UDP" 会判成 chat
  - 在 git 仓库里，且已经有编程关键词：agentic_coding 和 code_reasoning 各 +0.3；如果有代码块，coding_chat −0.5
- 工具集只作弱支持（+0.3），而且**必须已经有关键词命中才加分**，因为每条消息都会带着全部工具集。实测中 Hermes 并不把 `enabled_toolsets` 传给 hook，所以这一项目前基本不起作用。

**判断档次**（从类型的默认档出发，加减后四舍五入）：

| 信号 | 调整 |
|---|---|
| 范围大："整个 / 从零 / 所有 / entire / from scratch …" | +1 |
| 范围小："简单 / 一行 / quick / typo / just …" | −1 |
| 编程类型，且消息里有 3 个以上路径 | +1 |
| code_reasoning，消息里最多 1 个路径，且没有"范围大"的说法（单文件） | −1 |
| agentic_coding 或 code_reasoning，且仓库超过 5 万行 | +0.5 |
| 消息超过 1500 token（详细需求） | +0.5 |
| long_doc，且附件 ≥ 3 个 | +1 |
| `context_tokens_now` 超过 150k | +1 |
| **agentic_coding，不在 git 仓库里，消息里也没有路径（独立脚本）** | −1；消息不到 20 token 时再 −0.5 |

**第一批真实数据（Justin，Sonnet，7 个任务，11/6）带来的修正**：单文件的解释只用了 2 次调用，所以单文件的 code_reasoning 降一档；"add in_stock() + 一行检查"原来被判成 chat，所以补了标识符信号和"add … function/check"的说法；"Explain TCP vs UDP"原来被判成 code_reasoning / M，所以泛用的解释词改成需要代码上下文；派子 agent 时主 agent 主要是在协调，默认档从 L 降到 M。这些案例都写进了 `tests/test_eval_regressions.py`。

"独立脚本"这一条来自 Justin 的第一次实测：Haiku 收到 "write a fib script, save and run it"，只用了 2 次调用。修正前这句话被判成 chat，补上英文规则后又变成 L 级 20 步，加了这一条后才变成 S 级。

**其他输出：**
- **图片张数**：从 "3 张""三张""4 images" 这类说法里解析，默认 1 张，最多 50 张。
- **子 agent 个数**：从 "3 个方向""5 subagents" 这类说法里解析；没写时默认 P50 为 2、P90 为 4。
- **置信度**：L1 本身就弱，所以置信度最高只给到 0.45，由第一名和第二名的得分差决定。没有任何信号的消息：不到 10 token（如"你好"）给 0.5；更长的给 0.3，因为它可能是含义模糊的任务请求，交给 L3 判断。

## 3. 开工前的预测 `estimate()`（`estimator.py`、`history.py`、`textvec.py`）

```
L1：类型、档次、步数先验 K、形状 (g, o, h)、子 agent 段
  → L2（如果有相似的历史任务）：迁移步数 K 和形状 (g, o, h)，在 log 空间里向 L1 收缩
  → 用当前的 L_1 重新计算 token（底数和上下文变化会自动反映进来）
  → 校准（如果完成的任务达到 3 个）：修正 P50 的偏差，按覆盖率设定 P90（第 4 节）
```

**L2 的细节：**
- **文本表示**：词（每个汉字算一个词）的 1–2 gram，加上字符的 3–5 gram，用 crc32 哈希到 2^18 个桶，再算 TF-IDF（次线性 TF + 平滑 IDF）和余弦相似度。只存桶的计数，不存原文。
- **近邻**：相似度 ≥ 0.2 的前 8 个；只用 `completed` 和 `stopped` 的记录。
- **迁移的内容**：每条记录存了实际的步数 K、起始 prompt L_1、g（由总 prompt 反解）、每步输出 o 和缓存命中率 h。**迁移的是形状，不是 token 绝对值**，这样换了底数或模型上下文后照样适用。
- **收缩**：λ = Σ相似度 / (Σ相似度 + 2)。P50 = exp(λ·历史加权中位数 + (1−λ)·log K_L1)。P90 的宽度需要更多数据才可信，按 n/(n+5) 在历史宽度和先验宽度之间混合，且 P90 至少是 P50 的 1.3 倍。
- **被拦停的任务（stopped）**：作为下限处理，步数 ×1.5，权重减半。这只是临时做法，以后由 hazard 模型替代。
- **置信度**：max(L1 置信度, 0.25 + 0.5·λ)，最高 0.8。
- **子 agent 段**：沿用 L1 算出的子 agent 部分，叠加在 L2 重算的主 agent 上。

**未实现**：按模型做 token 归一化。TokenCast 中，同一任务在 Opus 和 GPT 上相差 1.05–1.8 倍。目前迁移的是步数和形状，可以部分抵消这种差异；但不同模型的步数本身也不一样，这一点还没有处理。

### 3.1 L3 便宜模型（`l3.py`）

- **调用条件**：harness 传进来的 `llm` 自带一个实时的 `.mode` 属性，每次调用都会读取，所以改了设置不用重启。
  - `always`：每条非空消息都调用（用于 demo）。
  - `auto`：只在 L2 没有近邻、并且 L1 置信度低于 0.4 时调用。很短的闲聊（不到 10 token）L1 置信度给 0.5，所以不会触发；稍长但没有任何信号的消息置信度只给 0.3，会交给 L3 判断。
  - `off`，或者 `llm=None`：不调用。
- **问什么**：让模型只返回 JSON，包括 task_type、tier、steps_p50、steps_p90、images。只问步数，不问 token。提示词里会说明"一步 = 一次模型调用"，并给出各档的典型步数；同时附上是否在 git 仓库里、仓库行数、所用模型。消息截断到 1500 字符。
- **怎么合并**：
  - 步数：先乘以学到的低估系数，再在 log 空间里以 0.3 的权重并入 P50。
  - **它给的区间完全不用**，P90/P50 的比例沿用 L1/L2 草稿的值，因为论文显示模型自评的 90% 区间实际只覆盖 52.7%。
  - 类型：只有 L1 置信度 ≤ 0.3 时，才采用 L3 判断的类型，每步形状 (g, o) 取两种类型的平均。
  - 图片张数：类型是 generation、且 L3 给的张数比 L1 多时，用 L3 的。
- **低估系数**：从记录中取"实际步数 / L3 步数"的 log 中位数，按 n/(n+5) 向先验 1.25 收缩。先验 1.25 是猜的：论文只说模型会系统性低估，没有给出具体幅度。
- **失败处理**：没有 `llm`、harness 返回 `None`（没授权、当前 provider 没有便宜模型、出错、超过 4 秒），或者 JSON 解析失败，都直接沿用 L1/L2 的结果，不报错。
- **隐私**：L3 会把用户的消息发给用户自己所用的 provider。harness 的 README 和提交说明里都已经写明。

## 4. 区间校准（`calibration.py`）

- **数据来源**：每条 L2 记录同时存了开工时**发出去的** P50/P90（`p50`/`p90`，用于统计覆盖率）和**校准前的草稿**（`d50`/`d90`，来自 `shape.draft_p50/p90`，用于估计偏差和区间宽度）。校准结果直接从 `l2_records` 推导出来，**没有新增状态 key**，每个任务结束仍然只写一次。早期没有这些字段的记录会被跳过。
- **偏差**：对已完成的任务计算 r = log(实际 / 草稿 P50)，取中位数，按 n/(n+10) 收缩。然后每种任务类型再加一个相对全局的偏移量，同样按 n/(n+10) 收缩（至少要有 2 条记录）。
- **必须和草稿比，不能和自己的输出比**：如果拿"实际 / 已校准的预测"来估偏差，预测越准，算出的偏差就越小，校准量又被拉回去。模拟中，用户任务比默认便宜 3 倍时，修正前 P50 仍偏差 1.74 倍，修正后只偏差 1.05 倍。
- **P90**：对去掉偏差后的残差取 conformal 分位数（第 ⌈(n+1)q⌉ 小的值）。分位水平用 ACI 在线调整：按时间顺序重放全部记录，α ← α + 0.05·(0.1 − 是否超出 P90)，α 限制在 [0.005, 0.5]。数据少时按 n/(n+10) 和先验宽度混合，且 P90 至少是 P50 的 1.3 倍。
- **被拦停的任务（stopped）**：不参与偏差估计；只有在被拦停时已经超过 P90，才算一次未覆盖，否则跳过（右删失）。
- **怎么应用**：主 agent 和子 agent 两部分按**同一个系数**缩放（只缩放主 agent 曾导致派子 agent 的任务步数塌到 0.1，Justin 的实测里发现）。主 agent 部分用二分法反解出能得到目标总量的步数 K，且至少 1 步；`shape.subagents` 里的子 agent 个数也按同样的系数缩放。这样 `shape` 和 `projected_steps` 与校准后的总量保持一致，harness 计价时用的就是校准后的结果。
- **生效条件**：完成的任务至少 3 个。只作用于开工前的预测，不作用于 reforecast。
- **模拟验证**（每组 160 个任务，统计后一半，见 `test_calibration.py`）：

| 场景 | P90 覆盖率（目标 90%） | P50 偏差 |
|---|---|---|
| 噪声很大（σ = 1） | 69% → **91%** | 1.34 倍 → 1.23 倍 |
| 用户任务比默认便宜 3 倍 | 99% → **91%** | 2.89 倍 → **1.05 倍** |
| 用户任务比默认贵 3 倍 | 80% → **89%** | 1.32 倍 → 1.19 倍 |

- **已知的相互作用**：L2 和校准都从同一批记录中学习，前期两者可能叠加修正。等有真实数据后再检查。

## 5. 跑到一半重新预测 `reforecast()`（`midtask.py`，产品价值所在）

最终总量 = 已花费 + 剩余部分。结果**不会低于已花费**。

1. **重新估计每步形状**：取最近 10 次调用的 `prompt_tokens`，用最小二乘斜率得到 ĝ；输出取中位数得到 ô；缓存命中率 ĥ = cache_read / (cache_read + input)。然后按 n/(n+3) 与开工时的形状混合。下一次调用的 prompt = 最后一次的 prompt + ĝ。
2. **剩余步数 K_rem**，在 log 空间里依次合并以下信号：
   - **先验**：把开工预测的 (P50, P90) 看作对数正态分布，在"总步数 > 已执行步数 k"的条件下，取剩余步数的 P50 和 P90。
   - **计划进度**（`todo_list`，TokenCast 中重要度 0.25）：剩余条数 × 已观察到的每条平均步数（还没完成任何一条时，用开工预测的 P50 除以总条数）。权重 = 0.5 + 0.4 × 完成比例，最高 0.9。P50 和 P90 都按这个权重混合，P90 侧使用"计划值 × 1.8"。
   - **阶段**（只用于 agentic_coding 和 code_reasoning，且 k ≥ 3）：按 2.2 节由阶段推算剩余步数，权重 0.25。
   - **失控信号**（会一起乘到剩余步数上，最多 2.5 倍；P90 额外再乘 1.3，因为不确定性涨得比中心值快）：
     - 连续无进展的调用：每次 +15%（TokenCast 重要度 0.23）
     - 最近 8 次工具调用中失败 ≥ 2 次：每次 +10%
     - 最近 12 次工具调用中，同一文件被读改 ≥ 3 次：每多一次 +10%（2604.22750 图 4）
     - 重试 ≥ 2 次：+10%
   - P90 至少是 P50 的 1.3 倍。
3. **剩余 token**：从下一次调用的 prompt 开始、缓存为热，用 `project(K_rem, ...)` 计算。
4. **子 agent**：开工时预计要派、但 `features.subagents` 仍为空的子 agent，继续计入；一旦有子 agent 启动，就不再单独计入，因为它们的用量已经包含在已花费里。
5. **置信度**：随进度上升，conf₀ + (0.9 − conf₀) × 进度，进度 = k / (k + K_rem)。
6. **`shape.steps_done = k`**，所以 `projected_steps` 只返回剩下的调用。

**harness 的用法**：每次 API 调用后都调用 `reforecast`，用剩余调用的 **P50** 逐步计价，再加上已花的钱，得到"预计总价"，作为预算拦截的依据（软停用 `approve`，到上限时硬停用 `block`）。如果想提前给出软提醒，可以改用 P90。

**模拟验证**（`test_reforecast.py`：真实运行 14 步、7 条待办；开工预测为 L 级、20 步）：

| 时间点 | 预测总步数 | P50 token 误差 | 真实值在 P90 内？ |
|---|---|---|---|
| 开工时 | 20 | 47% | 是 |
| 第 3 步 | 20.6 | 61% | 是 |
| 第 7 步 | 17.7 | 35% | 是 |
| 第 11 步 | 16.6 | 24% | 是 |

第 3 步的误差比开工时还高，因为观察到的上下文增长比先验快，而计划才完成 1/7，计划信号还很弱。这些都是构造出来的数据，真实准确率要等评估时再测。

**暂用简化版**：DESIGN 6.5 第 2 条的风险模型（hazard model）。目前的"对数正态条件先验 + 计划、阶段、失控信号"是不需要训练的替代方案。

## 6. harness 提供的特征（已全部实现，#28）

`contracts.TaskFeatures` 中，任务运行时会持续填入的字段：

| 字段 | 来源 hook | 算法中的用途 |
|---|---|---|
| `step_usages`（每步 `Usage`，含 cache_write 和 prompt_tokens） | `post_api_request` | reforecast 重新估计 ĝ、ô、ĥ；L2 记录的起始 L_1 |
| `step_tools`（工具名、成败、文件路径） | `pre_tool_call` / `post_tool_call` | 阶段识别、工具失败、重复读改同一文件 |
| `reasoning_effort` | Hermes 配置 | 每步输出的系数 |
| `tool_errors`、`retries`、`no_progress_calls` | `post_tool_call` / `api_request_error` | 失控信号 |
| `plan_items {total, done}` | `todo_list` 的调用参数 | 剩余步数 |
| `subagents`（按子会话 ID 归集的用量和模型） | `post_api_request` + `subagent_start/stop` | 判断子 agent 是否已经启动 |

**拿不到的字段**：`enabled_toolsets`（Hermes 不传给 hook）和 `attachments`（`pre_llm_call` 不传）。所以 L1 里工具集这个弱信号，以及 long_doc 的附件信号，目前都不起作用。

## 6.5 算法升级（第二轮文献调研后提出）及当前状态

1. **分层经验贝叶斯收缩** —— ⚠️ 部分实现
   - 校准已经做了"全局 → 任务类型"两层收缩。
   - L2 用的是按相似度总和的收缩（λ = Σsim/(Σsim+2)），不是计划中"全局 → 类型 → (类型, 档次) → 相似任务"的完整层级。
   - 参照：arXiv 1803.01440、arXiv 1809.02213。
2. **用离散时间风险模型（hazard model）预测剩余步数** —— ❌ 未实现，暂用第 5 节的简化版
   - 每一步估计 P(在第 k 步结束 | 还没结束, 阶段, 无进展次数, 报错次数, 重复读写次数)，用 logistic 回归拟合，天然支持右删失。
   - 有了真实轨迹后再做。参照：arXiv 2609.29508。
3. **在线自适应 conformal（ACI）** —— ✅ 已实现（第 4 节）
4. **子 agent 作为独立段** —— ✅ 已实现（底数 52.6k，个数从消息中解析）
5. **"重复读改同一文件"作为失控信号** —— ✅ 已实现（第 5 节）

## 8. 评估（`eval/`）—— ⏸ 暂缓

目前的准确率数字只来自 `tests/` 里的模拟数据（第 4、5 节）。等恢复评估时，计划如下：

- 20 到 30 个任务，按**类型 × 档次**分层抽样：每种类型至少 3 个，agentic coding 多放一些（因为最难预测）。每个任务至少跑 2 次（同一任务方差很大）。必须用 **API key** 跑，不能用订阅登录（plan 第 1 节）。
- 对比对象：
  - 历史中位数（TokenCast 的归一化基准）
  - 只用 L1
  - L1 + L2
  - L1 + L2 + 校准
  - Self-Prediction（直接问主模型）
- 指标：log 空间的 MAE 和 WAPE；P90 的实际覆盖率（目标约 90%）；档次准确率；reforecast 在进度 25%、50%、75% 时误差各下降多少。结果按类型分别报告。
- 原则：准确率要实际测出来，不能直接照搬论文数字或模拟结果。
